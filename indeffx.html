Chapter 01

Why MCP and Why Now

The Model Context Protocol is not a library. It is an infrastructure primitive — the same way TCP/IP is not an app but the layer that makes apps possible. MCP defines how AI agents discover, call, and receive results from external tools in a standardized, transport-agnostic way.

Before MCP, every AI integration was bespoke. Claude had its own tool format. OpenAI had function calling. AutoGen had its own schema. Each agent runtime spoke a different dialect. Developers maintained N different integration layers for the same underlying tools.

MCP ends that. One server. Any client. The protocol handles discovery, schema, execution, and error propagation. Your tool becomes universally callable — by Claude Desktop, Cursor, VS Code Copilot, AutoGen, CrewAI, or any runtime that implements the protocol.

The Operator Advantage

Infrastructure shifts create asymmetric opportunities. The developers who understood REST in 2005 built the APIs that everything runs on today. The developers who understood containers in 2014 built the deployment patterns everyone copies. MCP is that moment for AI agent tooling.

⚡ Operator Signal

The question is not whether MCP becomes the standard. The question is whether you are building on it before or after everyone else. The playbook you are reading right now is the answer.

Chapter 02

mcp-forge Architecture

mcp-forge is a FastAPI-style framework for the Model Context Protocol. Its core insight: the most painful part of building MCP servers is not the business logic — it is the plumbing. JSON schema generation, input validation, transport dispatch, error serialization. mcp-forge automates all of it.

The ForgeApp Object

ForgeApp is the central object. It holds the tool registry, manages transport lifecycle, and exposes the MCP-compliant interface. You instantiate it once and hang tools off it with the @app.tool() decorator.

from mcp_forge import ForgeApp app = ForgeApp( name="my-server", version="1.0.0", description="Production MCP server" )

Decorator Resolution

When you decorate a function with @app.tool(), mcp-forge inspects the function signature at import time. It reads the type annotations and the Pydantic input model to generate a fully-compliant MCP JSON schema automatically. No manual schema writing. No drift between code and schema.

Transport Dispatch

mcp-forge supports three transports from the same codebase. STDIO is the standard for local clients like Claude Desktop. HTTP exposes the server as a web service. SSE adds streaming support for long-running tools. You select the transport at runtime with a single flag — the tool code never changes.

TransportUse CaseFlag
STDIOClaude Desktop, local agents--transport stdio
HTTPRemote clients, custom integrations--transport http
SSEStreaming, long-running tools--transport sse
Architecture Note

The transport layer is completely decoupled from tool logic. A tool you write today for Claude Desktop runs unchanged as an HTTP endpoint tomorrow. This is the operator advantage of building on the right abstraction.

Chapter 03

Building Your First Production Tool

Install mcp-forge and build a production-ready tool in under 10 minutes. This chapter walks every step from zero to a running, testable MCP server.

Step 1 — Install

pip install mcp-forge

Step 2 — Define Your Tool

server.py
from mcp_forge import ForgeApp from pydantic import BaseModel, Field from typing import Optional app = ForgeApp("operator-server") class SearchInput(BaseModel): query: str = Field(..., description="Search query string") limit: int = Field(10, ge=1, le=100, description="Max results") filter_tag: Optional[str] = Field(None, description="Filter by tag") @app.tool() async def search(input: SearchInput) -> dict: # your business logic here results = run_search(input.query, input.limit, input.filter_tag) return {"results": results, "count": len(results)}

Step 3 — Run

# STDIO (Claude Desktop) python server.py --transport stdio # HTTP (port 8000) python server.py --transport http --port 8000 # SSE (streaming) python server.py --transport sse --port 8001

Step 4 — Connect to Claude Desktop

Add to your claude_desktop_config.json:

{ "mcpServers": { "operator-server": { "command": "python", "args": ["/path/to/server.py", "--transport", "stdio"] } } }
Operator Checkpoint

At this point your tool is live, schema-validated, and callable by any MCP client. That is the output of 10 minutes with mcp-forge vs. 2 hours of manual wiring.

Chapter 04

Input Validation That Actually Works

Bad input kills agents. When a tool fails silently, the agent retries, hallucinates a workaround, or crashes. mcp-forge uses Pydantic v2 to validate every input before your tool code runs — and surfaces errors in a format agents can act on.

Core Patterns

from pydantic import BaseModel, Field, field_validator from typing import Literal, Optional from datetime import date class ReportInput(BaseModel): # Required with description (shows in MCP schema) repo: str = Field(..., description="GitHub repo slug e.g. owner/repo") # Literal enum — agent can only pass valid values format: Literal["json", "markdown", "csv"] = "json" # Optional with default since: Optional[date] = None # Bounded integer max_items: int = Field(50, ge=1, le=500) # Custom validator @field_validator("repo") def validate_repo_slug(cls, v): if "/" not in v: raise ValueError("repo must be in owner/repo format") return v

Nested Models

For complex tools, nest Pydantic models. mcp-forge generates the nested JSON schema automatically and validates the full depth before execution.

class PaginationConfig(BaseModel): page: int = Field(1, ge=1) per_page: int = Field(20, ge=1, le=100) class ListInput(BaseModel): query: str pagination: PaginationConfig = PaginationConfig()
Why This Matters

Pydantic validation errors are automatically serialized into MCP error responses with field-level detail. The agent receives a structured message it can parse — not a traceback it cannot act on.

Chapter 05

Testing Like an Operator

You should know your MCP server works before the agent finds out it doesn't. ForgeTestClient lets you call tools directly in your test suite — no running server, no spawned process, no network calls.

ForgeTestClient Setup

test_server.py
import pytest from mcp_forge.testing import ForgeTestClient from server import app @pytest.fixture def client(): return ForgeTestClient(app) def test_search_returns_results(client): result = client.call( "search", {"query": "mcp-forge", "limit": 5} ) assert result["count"] <= 5 def test_search_validates_limit(client): with pytest.raises(ValidationError): client.call("search", {"query": "x", "limit": 999})

Operator Testing Checklist

  • Test every tool with valid input — verify the output shape
  • Test boundary values for every bounded field (min, max, edge)
  • Test invalid input — verify the error is a ValidationError, not a crash
  • Test missing required fields — the error message must be agent-readable
  • Test nested model validation depth
  • Run tests in CI before any deploy
Chapter 06

Multi-Transport Deployment

The same server.py file runs on STDIO, HTTP, and SSE. Deployment is a configuration decision, not a rewrite. Here are the production patterns for each target.

Docker

Dockerfile
FROM python:3.11-slim WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY . . EXPOSE 8000 CMD ["python", "server.py", "--transport", "http", "--port", "8000"]

Railway (60-second deploy)

# Install Railway CLI npm i -g @railway/cli # Deploy railway login railway init railway up # Set transport via env var railway variables set MCP_TRANSPORT=http

Fly.io

fly launch --no-deploy fly secrets set MCP_TRANSPORT=http fly deploy
Operator Pattern

Use STDIO for local dev and Claude Desktop. Use HTTP for any remote agent or custom client. Use SSE when tools run long jobs and need to stream progress back to the agent.

Chapter 07

Built-in Contribs

mcp-forge ships with a contribs library — pre-built tool implementations for the most common categories. One import. Zero boilerplate.

ContribWhat It Gives YouWhen to Use
memoryKey-value store, semantic searchAgent needs to remember context across calls
filesystemRead/write files, list directoriesTools that manipulate local or remote files
webHTTP fetch, HTML parsing, searchTools that need to retrieve web content
shellRun subprocess commands safelyAutomation tools, CI/CD integrations
dbSQLite and Postgres query toolsData retrieval and write operations

Using a Contrib

from mcp_forge import ForgeApp from mcp_forge.contribs import memory, web app = ForgeApp("operator-server") app.include(memory) app.include(web) # memory and web tools are now registered and schema-ready

Custom vs. Contrib

  • Use contrib when the category matches and you don't need custom business logic inside the tool
  • Build custom when the tool is specific to your domain, has non-standard validation, or needs to integrate with internal systems
  • Extend contrib when the base behavior is right but you need pre/post hooks

Designing Tools for Agents

When the caller is an agent, not a human, tool design changes. Agents retry on failure. Agents cannot read ambiguous errors. Agents may call the same tool 50 times in parallel. Design for that reality:

  • Be idempotent. The same input should always produce the same safe result.
  • Return structured data. Agents parse JSON — not prose. Every tool should return a typed, predictable schema.
  • Surface actionable errors. An error message of "something went wrong" is useless to an agent. Return the field, the constraint, and the received value.
  • Keep tools atomic. One tool does one thing. Compose at the agent layer, not inside the tool.
