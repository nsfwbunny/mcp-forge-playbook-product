Chapter 01

Why MCP and Why Now

The Model Context Protocol is not a library or a convenience wrapper. It is an infrastructure primitive in the same class as HTTP or the POSIX file descriptor: a universal contract that defines, once, how AI agents discover tools, call them, and receive structured results. Before MCP, every agent runtime spoke a different dialect. Claude had its own tool format. OpenAI had function calling. AutoGen and LangChain each had their own abstractions. Every developer who wanted to expose tools to multiple runtimes maintained N separate integration layers for the same underlying logic.

MCP ends that fragmentation. You write one server, register tools once, and every MCP-compatible client — Claude Desktop, Cursor, VS Code Copilot, JARVAS-2, or any future runtime that implements the spec — calls your tools without modification. The protocol handles discovery, schema negotiation, execution dispatch, and error propagation. Your business logic ships once and runs everywhere.

The Infrastructure Shift Window

Every major infrastructure primitive creates an asymmetric advantage for early adopters. REST standardized around 2000–2005; the developers who internalized it built the API-first companies that dominate cloud today. Docker reached critical mass 2014–2016; teams that built on containers then have a decade of operational depth that is nearly impossible to replicate quickly. MCP is in its 2014 Docker moment right now — young enough that most developers are still building the wrong way, mature enough that Anthropic, Microsoft, and every major AI IDE have committed to it as the standard.

⚡ Operator Signal

The question is not whether MCP becomes the standard — that decision has already been made by Anthropic, Microsoft, and the major AI IDEs. The question is whether you are building on it before or after the window closes.

Chapter 02

mcp-forge Architecture

mcp-forge is a FastAPI-style framework for MCP. Its thesis: the most painful part of building MCP servers is not the business logic — it is the plumbing. JSON schema generation from Python types, input validation, error serialization, transport lifecycle, tool registry maintenance. mcp-forge automates every one of those so you write tool logic only.

The ForgeApp Object

ForgeApp is the central object in every mcp-forge server. It holds the tool registry, manages transport initialization, exposes MCP capability negotiation, and handles the request/response cycle for every tool call. You instantiate it once and register tools with @app.tool().

from mcp_forge import ForgeApp app = ForgeApp( name="operator-server", version="1.0.0", description="Production MCP server — Benni-os stack" )

Schema Generation at Import Time

When Python imports your server module, every @app.tool() decorator fires immediately. mcp-forge inspects the decorated function's Pydantic input model, extracts every field with its type, default, constraints, and Field(description=...) metadata, and generates a fully-compliant MCP JSON Schema stored in the tool registry. Schema is zero-cost at request time and zero-drift from your code. Add a field to the Pydantic model and the schema updates automatically on next import — no separate schema file, no code generation step, no sync risk.

Transport Layer

mcp-forge ships three transports out of the box: STDIO for local agent integrations like Claude Desktop and Cursor, HTTP+SSE for long-running remote servers, and WebSocket for streaming use cases. You choose the transport at server startup; the tool code is transport-agnostic. A tool written for local STDIO testing deploys to HTTP+SSE production with zero changes.

Chapter 03

First Production Tool

A production tool in mcp-forge has three components: a Pydantic input model that defines the typed contract, a decorated async function that contains the business logic, and a structured return value that the agent runtime can reason about. The Pydantic model is the source of truth — it drives schema generation, input validation, error messages, and documentation simultaneously.

from pydantic import BaseModel, Field from mcp_forge import ForgeApp, ToolResult app = ForgeApp(name="my-server", version="1.0.0") class SearchInput(BaseModel): query: str = Field(description="Search query string", min_length=1) limit: int = Field(default=10, ge=1, le=100, description="Max results") include_metadata: bool = Field(default=False) @app.tool(description="Search the knowledge base and return ranked results") async def search_knowledge_base(inp: SearchInput) -> ToolResult: results = await run_search(inp.query, limit=inp.limit) return ToolResult( content=results, metadata={"count": len(results), "query": inp.query} )
💡 Pattern

Every tool should have exactly one Pydantic input model, one ToolResult return, and zero side effects outside its declared scope. This keeps tools composable, testable, and safe for agent orchestration chains where the same tool may be called 50 times in a session.

Naming and Description Discipline

The description field on @app.tool() and on every Field() is not documentation — it is the primary signal the LLM uses to decide whether and how to call your tool. Write descriptions as precise, action-oriented statements. "Search the knowledge base and return ranked results" is good. "Search" is not. "Searches the knowledge base for documents matching the query string and returns up to limit results sorted by relevance score" is better. The more precisely you describe the tool, the more reliably agents select it in the right context.

Chapter 04

Input Validation

Validation is your first line of defense in a production MCP server. Agents will call your tools with unexpected inputs — empty strings where text is required, negative numbers where positive integers are expected, enum values that have drifted from your schema. mcp-forge delegates all validation to Pydantic v2, which means your validation logic lives in the same place as your type definitions: the input model.

Custom Validators

For business logic that cannot be expressed with simple constraints — for example, "if mode is 'deep' then min_tokens must be at least 500" — use Pydantic's @model_validator. This runs after all field-level validation and has access to all fields simultaneously. Raise a ValueError and mcp-forge serializes it into a structured MCP error that the agent runtime can parse and report.

from pydantic import model_validator class AnalysisInput(BaseModel): mode: Literal["fast", "deep"] min_tokens: int = Field(default=100, ge=100) @model_validator(mode="after") def check_deep_tokens(self): if self.mode == "deep" and self.min_tokens < 500: raise ValueError("deep mode requires min_tokens >= 500") return self
Chapter 05

Testing Like an Operator

Production-grade MCP tools require three layers of testing: unit tests that validate tool logic in isolation, integration tests that validate the full MCP request/response cycle, and contract tests that validate schema stability across versions. Most developers do only the first layer and discover the other two failure modes in production.

Unit Testing Tool Logic

Because mcp-forge tools are plain async Python functions, you can call them directly in tests without starting a server. Pass a valid input model instance, assert on the ToolResult return. Use pytest-asyncio for async test support.

import pytest from myserver import search_knowledge_base, SearchInput @pytest.mark.asyncio async def test_search_returns_results(): result = await search_knowledge_base(SearchInput(query="mcp transport")) assert len(result.content) > 0 assert result.metadata["query"] == "mcp transport"

Integration Testing via MCP Client

mcp-forge ships a test client ForgeTestClient that starts your server in-process, sends real MCP protocol messages over STDIO, and returns parsed MCP responses. This tests the full stack including schema negotiation, capability exchange, and error serialization — the parts that unit tests miss entirely.

⚠ Operator Warning

Schema drift is the most common production failure mode for MCP servers. A tool that passed all unit tests can break agent integrations silently if a field was renamed or a constraint was tightened in a way that existing callers do not expect. Run contract tests on every deploy.

Chapter 06

Multi-Transport Deploy

A production MCP server needs to run in at least two modes: local STDIO for agent IDEs like Claude Desktop and Cursor, and remote HTTP+SSE for cloud-hosted agent runtimes, CI pipelines, and multi-tenant deployments. mcp-forge separates tool logic from transport so the same server binary handles both without any code changes.

STDIO Mode (Local)

STDIO transport is the default for local integrations. The agent runtime starts your server as a subprocess and communicates via stdin/stdout using the MCP JSON-RPC wire format. This is zero-configuration: no ports, no auth, no network. Claude Desktop, Cursor, and VS Code MCP extension all use this mode.

# pyproject.toml entry point [project.scripts] my-server = "myserver:app.run_stdio" # Claude Desktop config (~/.claude/mcp_servers.json) { "mcpServers": { "my-server": { "command": "my-server" } } }

HTTP+SSE Mode (Remote)

For remote deployments, mcp-forge starts an ASGI server (Uvicorn by default) that exposes the MCP HTTP+SSE transport on a configurable port. The /mcp endpoint handles capability negotiation and tool calls. The /mcp/events SSE stream delivers server-initiated messages and progress updates for long-running tools.

# Start remote server my-server --transport http --host 0.0.0.0 --port 8000 # Docker FROM python:3.12-slim RUN pip install my-server CMD ["my-server", "--transport", "http", "--host", "0.0.0.0", "--port", "8000"]

💡 Composition Pattern

The most powerful operator pattern is tool composition: build a high-level tool that calls two or three contribs in sequence. A research_topic tool that calls web_search, then http_fetch for each result, then summarizes — all inside one MCP tool boundary with one schema contract exposed to the agent.

Chapter 08

Operator Workflow

The operator workflow is the repeatable system that takes you from business requirement to deployed, monitored production tool. Most developers have the coding part but skip the upstream (requirement decomposition) and downstream (observability, versioning) steps. Those skipped steps are where production incidents originate.

The 5-Step Operator Loop

  1. Decompose — Define the tool's single responsibility. If you cannot describe what the tool does in one sentence without the word "and", split it.
  2. Model — Write the Pydantic input model first, before any logic. The model is your spec. Get it reviewed before writing business code.
  3. Implement — Write the async function. Keep it under 50 lines. If it is longer, extract helpers or split the tool.
  4. Test — Unit test, integration test, contract test. Do not deploy without all three passing.
  5. Observe — Every tool call should emit a structured log event with input hash, output hash, latency, and error type. mcp-forge's @app.tool(observe=True) flag does this automatically.

Versioning Strategy

MCP tool schemas are a public API. Agents build calling patterns around your schema — change a field name or tighten a constraint and you break those patterns silently. Version your tools with v1_search, v2_search naming and keep the previous version live during the transition window. mcp-forge's capability negotiation lets clients advertise which tool versions they support.

✅ Operator Checklist

Before deploying any tool to production: schema review done, contract test passing, observability enabled, error codes documented, rollback plan defined. These five gates prevent 90% of production MCP incidents.
